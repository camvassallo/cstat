# The 247Sports API, as cstat actually uses it

What we know about `ipa.247sports.com/rdb/v1/`, established by probing the live
service on **2026-08-19**. 247 publishes no documentation and makes no
compatibility promise, so treat every claim here as "true on that date, verify
before relying on it."

Companion to `docs/247_jwt_recapture.md` (the manual subscriber-token flow,
which the guest path below largely retires).

## Hosts

Two hosts serve the same `/rdb/v1/` path space.

| Host | Verdict |
| --- | --- |
| `ipa.247sports.com` | **Use this one.** Everything below was verified against it. |
| `api.247sports.com` | Returns HTTP 500 with an HTML error body on every route tried, authenticated or not. |

`api.247sports.com` is the host [sportsdataverse.js][sdv-recruiting] documents,
and its path list is accurate and useful — but its "auth required: No" column
does not reflect current behavior, and the host itself does not answer. Read it
for **route names**, then call those routes on `ipa`.

[sdv-recruiting]: https://js.sportsdataverse.org/docs/reference/recruiting

## Auth: three tiers

1. **No token** → `401` on every `/rdb/v1/` route.
2. **Guest token** → reaches everything cstat needs. Minted with no credential
   (below).
3. **Subscriber token** (`TFS_247_JWT`) → additionally reaches a handful of
   routes that 403 for guests.

### Minting a guest token

The public portal page embeds a server-minted guest JWT in its bootstrap JSON:

```
GET https://247sports.com/season/{year}-basketball/transferportal/
    (browser User-Agent)
→ 200 HTML containing  "jwt":"eyJhbGciOi…"
```

Decoded payload carries `"ss":"Guest"` and roughly a **12-hour** lifetime
(`iat`/`exp` ~43,200s apart). Send it as `Authorization: Bearer <jwt>`.

Implemented as `TfsClient::fetch_guest_jwt` / `from_env_or_guest`
(`crates/cstat-ingest/src/tfs.rs`). Precedence is `TFS_247_JWT` when set,
otherwise mint a guest token per run. The extraction is a regex over markup and
is therefore brittle to a 247 redesign — it has its own error variant
(`GuestJwtNotFound`) so callers can distinguish "layout changed" from "247 is
down" and fall back to a snapshot rather than treating it as an outage.

This is what makes an unattended run possible. The subscriber token expires ~6h
after issue with no renewal path, which is why ROADMAP S5/P3 originally declined
to schedule the 247 feeds at all.

### Gotchas that cost time

**Trailing slash is mandatory on the `rankings/...` sub-routes.** Without it you
get a `301` that `curl` will not follow by default, which reads as a dead route.

**The param set is not optional.** `commits/?sport=basketball&year=2026&page=1&pageSize=5`
returns **404**; the same route with the full
`listType=1&…&sportKey=2&…&yearSport=2026-basketball` set returns 200. A 404 here
means "wrong params", not "no such route".

**The row key differs per route.** `transfers/` and `recruits/` put rows under
`players[]`; `commits/` and `decommits/` use `list[]`. `transfers/` additionally
wraps each element in `{"player": {…}}`, which `TfsClient::parse_page` strips.
The others do not wrap.

**Pagination is not a clean partition.** Pages overlap and the same player
reappears with a *stale* status on a later page. Pages are newest-first, so the
ingest is first-write-wins on `tfs_key` (`apply_page`'s `seen` set). For the
2026 class this is dramatic: **2,920 rows paginate down to 1,573 unique keys.**
Any consumer that counts rows instead of distinct keys will overcount ~1.9×.

## Field notes

### `eligibility.years` is mostly null

On `transfers/`, 2,449 of 2,620 rows carry `null`. Ingested into
`transfers.eligibility_years` and read by nothing. Do not plan around it.

### `eligibleYears` on `commits/` is NOT eligibility

Populated 584/584, which makes it look like a 5-in-5 goldmine. It is not — the
values are `Senior 416 / Freshman 106 / Sophomore 41 / Junior 10 / NA 11`, i.e.
the recruit's **high-school grade at the time of commitment**. Nothing to do
with years of eligibility remaining. Do not wire it to anything eligibility-
related (issue #220).

### `commits/` carries much more than the HTML feed

`committedInstitution`, `institutionKey`, `announcementDate`, `earlySignee`,
`earlyEnrollee`, `grayShirt`, `walkOn`, `ranking`, `position`, `height`,
`weight`, hometown/state/country, plus `decommitRecruitInterestEvent`,
`officialVisitRecruitInterestEvent` and `recruitInterestCount`.

cstat currently ingests commits by **scraping the public HTML page** instead
(`Recruit247Client::public()` + `parse_commits_html`, keyed on
`li.ri-page__list-item`, 50 rows/page). That path is cookie-free and works — it
returned 586 rows across 12 pages on 2026-08-19, matching the JSON's 584 — but
it is a CSS-selector scrape where a JSON endpoint now exists. Migrating it is
open work, not done.

### `transfer_rank` goes stale mid-cycle

247 freezes the portal ranking after the spring window. Everyone entering later
carries `transfer_rank = NULL` — 1,023 of 1,542 non-withdrawn 2026 rows. `rating`
is the better sort key and is very nearly a monotone restatement of the rank:
over the 519 ranked rows, `corr(transfer_rank, rating) = -0.963`, on a shared
0.70–0.98 scale that also covers 414 of the unranked rows. `routes/transfers.rs`
orders by `rating DESC NULLS LAST, transfer_rank NULLS LAST, full_name` for this
reason.

## Year numbering

247's `year` is the **calendar year the portal class opened**, which is cstat's
**base** season, not the season being projected. The class that forms the
2026-27 rosters (cstat season 2027) is `year=2026`. `roster_projection` reads
`transfers WHERE year = base_season`, so the two line up directly.

Consequence worth remembering: `year=2027` returns `count: 0` today. That is
247 not having opened the class, not an error.

## Rate limiting

247 publishes no limit. cstat self-imposes 3,600 req/hr ≈ 1/sec
(`DEFAULT_RATE_PER_HOUR`, override `TFS_247_RATE_PER_HOUR`). A full `transfers`
sweep at `pageSize=25` is ~117 pages ≈ 2 minutes. Incremental mode
short-circuits once a page predates the DB cursor, so a nightly refresh is a
couple of requests.

## What the 5-in-5 rule changed

The portal is no longer a spring-only feed. Between 2026-08-01 and 2026-08-19,
**51 players entered the 2026 class**, and of the 56 August-window entrants that
resolve to a cstat player, **53 were `Sr`-labelled in 2026**. ROADMAP S5/P3's
premise — "zero in-season churn, the portal is a ~30-day spring window" — no
longer holds, and there is no reason to assume the window closes at tipoff.
`SeasonIngester::nightly` now refreshes the portal best-effort using the guest
token.

## Other sources evaluated, not adopted

**sportsdataverse** ([js][sdv-recruiting] /
[py](https://py.sportsdataverse.org/docs/0.0.73/mbb/)) wraps **ESPN** for
basketball — `site.api.espn.com`, `site.web.api.espn.com`,
`sports.core.api.espn.com`, no auth indicated. cstat's stack is
NatStat + Torvik + 247, so this is not a drop-in for anything we have. Two
things there are worth remembering if a need arises:

* **Injuries** (`espn…TeamInjuries` / athlete injuries) would be a real
  point-in-time availability feed, which cstat has never had. Note the prior
  finding before building on it: the raw effect is real (#1 CamPom player out ≈
  −2.3 pts vs Elo) but the point-in-time game model already absorbs it to ~0
  residual, so the expected value of wiring it up is low.
* **Play-by-play / rosters** overlap what NatStat already provides, with a
  different id space and no obvious gain.

Its recruiting module is the 247 wrapper described at the top of this document.
