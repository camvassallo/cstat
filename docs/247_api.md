# The 247Sports API, as cstat actually uses it

What we know about `ipa.247sports.com/rdb/v1/`, established by probing the live
service on **2026-08-19**. 247 publishes no documentation and makes no
compatibility promise, so treat every claim here as "true on that date, verify
before relying on it."

Companion to `docs/247_jwt_recapture.md` (the manual subscriber-token flow,
which the guest path below largely retires).

## Hosts

Two hosts serve the same `/rdb/v1/` path space.

| Host | Verdict |
| --- | --- |
| `ipa.247sports.com` | **Use this one.** Everything below was verified against it. |
| `api.247sports.com` | Returns HTTP 500 with an HTML error body on every route tried, authenticated or not. |

`api.247sports.com` is the host [sportsdataverse.js][sdv-recruiting] documents,
and its path list is accurate and useful — but its "auth required: No" column
does not reflect current behavior, and the host itself does not answer. Read it
for **route names**, then call those routes on `ipa`.

[sdv-recruiting]: https://js.sportsdataverse.org/docs/reference/recruiting

## Auth: three tiers

1. **No token** → `401` on every `/rdb/v1/` route.
2. **Guest token** → reaches everything cstat needs. Minted with no credential
   (below).
3. **Subscriber token** (`TFS_247_JWT`) → additionally reaches a handful of
   routes that 403 for guests.

### Minting a guest token

The public portal page embeds a server-minted guest JWT in its bootstrap JSON:

```
GET https://247sports.com/season/{year}-basketball/transferportal/
    (browser User-Agent)
→ 200 HTML containing  "jwt":"eyJhbGciOi…"
```

Decoded payload carries `"ss":"Guest"` and roughly a **12-hour** lifetime
(`iat`/`exp` ~43,200s apart). Send it as `Authorization: Bearer <jwt>`.

Implemented as `TfsClient::fetch_guest_jwt` / `from_env_or_guest`
(`crates/cstat-ingest/src/tfs.rs`). Precedence is `TFS_247_JWT` when set,
otherwise mint a guest token per run. The extraction is a regex over markup and
is therefore brittle to a 247 redesign — it has its own error variant
(`GuestJwtNotFound`) so callers can distinguish "layout changed" from "247 is
down" and fall back to a snapshot rather than treating it as an outage.

This is what makes an unattended run possible. The subscriber token expires ~6h
after issue with no renewal path, which is why ROADMAP S5/P3 originally declined
to schedule the 247 feeds at all.

### Gotchas that cost time

**Trailing slash is mandatory on the `rankings/...` sub-routes.** Without it you
get a `301` that `curl` will not follow by default, which reads as a dead route.

**The param set is not optional.** `commits/?sport=basketball&year=2026&page=1&pageSize=5`
returns **404**; the same route with the full
`listType=1&…&sportKey=2&…&yearSport=2026-basketball` set returns 200. A 404 here
means "wrong params", not "no such route".

**The row key differs per route.** `transfers/` and `recruits/` put rows under
`players[]`; `commits/` and `decommits/` use `list[]`. `transfers/` additionally
wraps each element in `{"player": {…}}`, which `TfsClient::parse_page` strips.
The others do not wrap.

**Pagination is not a clean partition.** Pages overlap and the same player
reappears with a *stale* status on a later page. Pages are newest-first, so the
ingest is first-write-wins on `tfs_key` (`apply_page`'s `seen` set). For the
2026 class this is dramatic: **2,920 rows paginate down to 1,573 unique keys.**
Any consumer that counts rows instead of distinct keys will overcount ~1.9×.

## Field notes

### `eligibility.years` is mostly null

On `transfers/`, 2,449 of 2,620 rows carry `null`. Ingested into
`transfers.eligibility_years` and read by nothing. Do not plan around it.

### `eligibleYears` on `commits/` is NOT eligibility

Populated 584/584, which makes it look like a 5-in-5 goldmine. It is not — the
values are `Senior 416 / Freshman 106 / Sophomore 41 / Junior 10 / NA 11`, i.e.
the recruit's **high-school grade at the time of commitment**. Nothing to do
with years of eligibility remaining. Do not wire it to anything eligibility-
related (issue #220).

### `commits/` carries much more than the HTML feed

`committedInstitution`, `institutionKey`, `announcementDate`, `earlySignee`,
`earlyEnrollee`, `grayShirt`, `walkOn`, `ranking`, `position`, `height`,
`weight`, hometown/state/country, plus `decommitRecruitInterestEvent`,
`officialVisitRecruitInterestEvent` and `recruitInterestCount`.

cstat reads both recruit feeds from JSON as of 2026-08-19
(`Recruit247Client::guest` + `parse_recruits_json` / `parse_commits_json`). The
HTML scrape it replaced is still selectable with `cstat-ingest recruits --html`,
because it is the only source for two columns (below) and a useful escape hatch
if 247 changes the JSON shape.

Two things to know before touching that code:

* **`compositeRating` is 0–100 on the JSON; the `recruits.composite_rating`
  column is 0–1.** Verified against the 363 rows that overlap the HTML-scraped
  2026 class — Tyran Stokes is `1.0` in the DB and `100` in the feed. The parser
  divides by 100. Get it wrong and a 100x feature reaches the freshman
  projection model with nothing to catch it.
* **`compositeStarRating` is not the composite star rating. Do not read it.**
  It is the field the rescale check above did not cover, and it is wrong in the
  direction that looks plausible — too many 5-stars. Three captured rows from
  the same class settle it:

  | Source | Player | Rank | Composite | Stars |
  | --- | --- | --- | --- | --- |
  | `recruits/` JSON | Ralph Scott | 76 | 0.9738 | **5** |
  | `commits/` JSON | Caleb Ourigou | 69 | 0.9763 | 4 |
  | rendered rankings page | ranks 51–100 | 51–100 | 0.9816–0.9535 | 4 (all 50) |

  The two JSON feeds disagree with each other *and* put the pair in the wrong
  order — the lower-rated, lower-ranked player is the one called a 5-star. The
  rendered page, which the HTML scrape reads by counting star glyphs, calls
  every player from rank 51 down a 4-star, so both of those are 4-stars.

  `tfs_recruits::composite_star_rating` therefore bands the 0–1 composite
  rating (`COMPOSITE_STAR_BANDS`: 5★ ≥ 0.9900, 4★ ≥ 0.8900, 3★ ≥ 0.7900, else
  2★) on both JSON feeds and ignores the field. The bands reproduce all 50
  ground-truth rows in `tests/fixtures/recruits_2026_hs_p2.html`
  (`star_bands_match_the_captured_rankings_page`). The 4/5 floor is the one the
  fixture only brackets — it starts at rank 51 and holds no 5-star row, so it
  proves the floor is above 0.9816 without pinning it; 0.9900 is 247's
  published figure. `scripts/audit_recruit_stars.sql` query 3 pins it against
  the HTML-scraped history, and the DB wins if they disagree.

  This matters past the recruit table: `star_rating` is served to the freshman
  and trajectory models as `recruit_star_rating`, declared **monotone
  increasing** in `training/train_freshman_model.py`. An inflated star is an
  inflated freshman projection and, through the roster-impact calibrator, an
  inflated preseason AdjEM for whoever signed the class. Training is unaffected
  — it draws on settled classes, which `class_is_live` never let the JSON
  transport overwrite — so this is a serving defect, not a retrain.
* **The commits feed has no signing signal.** `earlySignee` reads false on
  100/100 rows of the 2026 class — whose early period closed in November 2025 —
  and `signedInstitution`, which the rankings feed uses and populates on 66 of
  its top 100 for that same class, is not a key on this feed at all. So a
  commits-owned row is only ever `Committed` or `Uncommitted`, never `Signed`.
  That is a provenance asymmetry rather than a wrong row: the projection only
  tests `<> 'Uncommitted'` and is unaffected, but any UI presenting the
  Signed/Committed split as a confidence gradient would be reading provenance on
  the part of the table the commits feed owns.

  **In practice no row is affected, and the reason is load-bearing.** A
  commits-owned row is reclaimed by the next rankings pass — `upsert_player` has
  no ownership guard and overwrites `institution_group`, while `upsert_commit`'s
  `DO UPDATE` is guarded to commits-owned rows only — and the rankings feed is a
  strict superset of the commits feed, so it sees everything. Verified
  2026-08-20: commits-only rows number **0** for both live classes (2026:
  712 vs 584; 2027: 415 vs 61), the table carries zero commits-owned rows, and
  `Signed` is fully populated (2026: 305, matching the feed exactly). That
  superset property is an observation about 247's data, not a contract — if it
  ever breaks, the affected rows silently lose the ability to report `Signed`.
  Tracked as issue #260; do not reorder the nightly's recruit steps without
  reading it.
* **The commits feed keys on `playerKey`, not `key`.** On the same row `key` is
  the recruit-interest id, a different number. `playerKey` is what matches the
  rankings feed's `key` and the `recruit_key` already in the table (607 of 712
  2026 rows join).

### What the JSON does not carry

| Column | Rankings | Commits | HTML |
| --- | --- | --- | --- |
| `height` / `weight` / `high_school` | absent | present | present |
| `previous_rank` | absent | absent | present |
| `committed_school_slug` | absent | absent | present |

`previous_rank` has **no JSON source on any route probed** — it is not on
`recruits/`, `commits/`, or either `rankings/…` feed. It is an input to
`recruit_rank_movement` in the served freshman and trajectory models, so the
composite upsert COALESCEs it (and the other four) instead of overwriting:
a JSON pass can add to the column but never blank it. New classes ingested
JSON-only will simply have it NULL, which the feature already treats as
zero movement.

`height` is likewise a served model input, so `upsert_commit` gap-fills the
three physical columns onto a rankings-owned row when they are NULL there —
otherwise a class ingested rankings-first would keep NULL heights forever.
Verified after a live 2026 run: every row the commits feed covers has a height;
the 105 that don't are uncommitted players absent from that feed, who never
reach a roster.

### `transfer_rank` goes stale mid-cycle

247 freezes the portal ranking after the spring window. Everyone entering later
carries `transfer_rank = NULL` — 1,023 of 1,542 non-withdrawn 2026 rows. `rating`
is the better sort key and is very nearly a monotone restatement of the rank:
over the 519 ranked rows, `corr(transfer_rank, rating) = -0.963`, on a shared
0.70–0.98 scale that also covers 414 of the unranked rows. `routes/transfers.rs`
orders by `rating DESC NULLS LAST, transfer_rank NULLS LAST, full_name` for this
reason.

## Year numbering

247's `year` is the **calendar year the portal class opened**, which is cstat's
**base** season, not the season being projected. The class that forms the
2026-27 rosters (cstat season 2027) is `year=2026`. `roster_projection` reads
`transfers WHERE year = base_season`, so the two line up directly.

Consequence worth remembering: `year=2027` returns `count: 0` today. That is
247 not having opened the class, not an error.

## A recruit row is a living document, not an archival record

The single most important rule when re-fetching recruit classes, enforced by
`ingest::recruits::class_is_live`. 247 keeps editing a recruit's row long after
he is on campus, and two columns drift in ways that are actively wrong for
cstat's purposes:

* **`committedInstitution` becomes the school he transferred to.** Across the
  class-of-2014..2025 rows already stored, 1,592 had a different school in the
  JSON than the HTML scrape recorded — and where it could be checked against box
  scores, the *old* value matched the team he actually played his freshman
  season for (7 of 8). Taking the new value silently re-points a recruit at a
  team he reached two years later, which is backwards for a freshman-arrival
  model.
* **`compositeNationalRank` is re-based.** It disagrees with the scrape on 3,541
  historical rows, and not randomly: drift is ~0 at the top of a class and grows
  with depth (+45.7 by rank 500 for 2019). The scraped rank is internally
  consistent with the stored `composite_rating` (mean |rank − rating-order| =
  0.58); the JSON's is not (48.0). Whatever pool 247 ranks against now is not
  the one the stored ratings came from, and mixing them yields a column that
  agrees with neither.

So the upserts branch on whether the class is still live:

| Class | Behaviour |
| --- | --- |
| Live (`year >= current_natstat_season()`) | Feed is authoritative and overwrites. A NULL clears — that is how a decommit lands, and the reason a nightly refresh is worth running at all. |
| Settled | May add rows and fill NULLs; never overwrites. The stored value is the contemporary one, and it is what the served freshman and trajectory models were trained on. |

`raw_player` is frozen on the same rule rather than always-current: it is the
forensic copy of the record the parsed values came from, so overwriting it on a
settled class would destroy the last copy of the contemporary 247 record — the
very thing the freeze protects — and leave an audit trail that no longer
reproduces its own row.

The boundary is where it belongs: class C first plays in season C+1, so a class
stops being live at exactly the November rollover that puts its players into box
scores — the same moment the nightly's ingest window stops covering it. Same
shape as the rule `scripts/sync_to_prod.sh --columns` applies: merge past
seasons, let the live side own the current one.

**Known gap, not yet fixed (issue #259):** a decommit clears `commit_status` to
`Uncommitted` but nothing clears the already-resolved `committed_team_id`
(`resolve_team_joins` only considers rows with a non-NULL `committed_school`).
The roster projection filters those rows out by `commit_status`, but the
`peer_class_strength` subquery behind the freshman model does not — so a
decommitted recruit keeps contributing his rating to his former school's class
average (65 such rows across 12 seasons today, all of them carrying a rating).
Training computes the feature the same way, so there is no train/serve skew right
now; correcting it means a freshman-model retrain and everything below it, which
is why it is recorded rather than quietly patched.

## Rate limiting

247 publishes no limit. cstat self-imposes 3,600 req/hr ≈ 1/sec
(`DEFAULT_RATE_PER_HOUR`, override `TFS_247_RATE_PER_HOUR`). A full `transfers`
sweep at `pageSize=25` is ~117 pages ≈ 2 minutes. Incremental mode
short-circuits once a page predates the DB cursor, so a nightly refresh is a
couple of requests.

## What the 5-in-5 rule changed

The portal is no longer a spring-only feed. Between 2026-08-01 and 2026-08-19,
**51 players entered the 2026 class**, and of the 56 August-window entrants that
resolve to a cstat player, **53 were `Sr`-labelled in 2026**. ROADMAP S5/P3's
premise — "zero in-season churn, the portal is a ~30-day spring window" — no
longer holds, and there is no reason to assume the window closes at tipoff.
`SeasonIngester::nightly` now refreshes the portal best-effort using the guest
token.

## Other sources evaluated, not adopted

**sportsdataverse** ([js][sdv-recruiting] /
[py](https://py.sportsdataverse.org/docs/0.0.73/mbb/)) wraps **ESPN** for
basketball — `site.api.espn.com`, `site.web.api.espn.com`,
`sports.core.api.espn.com`, no auth indicated. cstat's stack is
NatStat + Torvik + 247, so this is not a drop-in for anything we have. Two
things there are worth remembering if a need arises:

* **Injuries** (`espn…TeamInjuries` / athlete injuries) would be a real
  point-in-time availability feed, which cstat has never had. Note the prior
  finding before building on it: the raw effect is real (#1 CamPom player out ≈
  −2.3 pts vs Elo) but the point-in-time game model already absorbs it to ~0
  residual, so the expected value of wiring it up is low.
* **Play-by-play / rosters** overlap what NatStat already provides, with a
  different id space and no obvious gain.

Its recruiting module is the 247 wrapper described at the top of this document.
